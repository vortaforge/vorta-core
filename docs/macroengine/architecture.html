Architecture

The rules the split is built on, and what enforces them.

The shape

One core pack and 28 module packs. Every module declares macroengine-core as a dependency. The core declares no module.

macroengine-core
   ├── macroengine-cmd
   ├── macroengine-player
   ├── macroengine-perm
   └── … 25 more, each depending only on core

Rule 1: no module depends on another module

A module may call the core by fully-qualified id. It may not call a sibling. The reason is not tidiness: it is the difference between a module you can delete and one you cannot. Two packs that call each other can only be installed together, and a user who installs one of them gets a pack that references ids that do not exist.

Where one feature genuinely needs another, the call goes through a hook slot the core owns.

Hook slots

The core defines an empty tag:

# me_core_module, tags/function/hook/events_fire.json
{ "replace": false, "values": [] }

The implementing module writes the same tag id from its own pack, listing its own function. The game merges them.

# me_events_module, same tag id
{ "replace": false,
  "values": [ { "id": "me_events_module:events/fire", "required": false } ] }

The caller names the slot, never the implementation:

# in the core
function #me_core_module:hook/events_fire with storage macroengine:engine queue[0]

With the events module installed the queue drains. Without it the slot is empty and the queue fills — which is what “the event module is not installed” should mean. Neither case is an error.

with storage … survives the rewrite. The arguments after the id are not touched, so a slot call keeps its payload. The same holds for the arguments on a plain function call.

Rule 2: the core does not name a module

The consequence of rule 1, stated from the core’s side. If the core calls me_events_module:events/fire directly, the events module is no longer optional, whatever the manifest says.

Rule 3: core holds the engine, not a toolbox

The core contains the internals, the gates, load and tick, and the kernel services the engine calls at boot: math, rng, log, string, color, validate. A pack the engine cannot boot without is part of the engine.

The same test sends features the other way. systems/text and systems/geo were in core and are now modules, because nothing in the engine called them — they were a general-purpose toolbox sitting in the kernel.

Rule 4: a tag may not require another module

A tag in one pack that lists another pack’s function has to mark that value optional:

{ "id": "me_input_module:input/anvil", "required": false }

As a plain string, the game fails the tag when the other module is absent. me_core_module:loop did exactly that with four input functions. Naming the core itself is fine: the core is never absent.

What enforces this

Four checks, all in CI. Each exists because its rule was broken at least once.

CheckWhat it proves
verify.py Every reference resolves, no module reaches another’s internals, the core names no module, no foreign-module tag value is mandatory, and the dependency graph is acyclic.
check_refs.py Every namespace:path token in every pack exists. Catches an id the split failed to rename, which is otherwise found only when the game refuses the pack.
test_module_removal.py Deletes each module in turn and re-verifies the rest — 29/29. This is the claim the split exists for, tested rather than asserted.
test_check_refs.py Breaks the output in each id shape that has broken a real server, and asserts check_refs reports it. A checker that has never failed is not evidence.
Why so much checking. Every defect below shipped in a release and was found by booting a server and reading the log, not by a test: an entry point that did not implement ModInitializer and stopped the whole server; a dialog id that made the registry refuse to load; execute if predicate and dialog show ids left pointing at a namespace that no longer existed; an SNBT {func:"…"} payload that silently never ran. Each is now a test.

The data pack layout

Each module is a complete data pack: its own pack.mcmeta, its own namespace, and no dependency on another pack’s files. The jar root holds exactly what the game expects, so the same file works in mods/ and in datapacks/.

Cross-pack references are the one thing that is not free. Every me_<module>_module: id inside a module must point at the core or be a tag value, and both are checked.

The tick and load spine

Exactly two entry points, both in the core, both vanilla function tags:

  • #minecraft:load — runs the load gate, then initialises scoreboards, storages and player state.
  • #minecraft:tick — drives the scheduler, then calls the per-feature tick slots. Each feature attaches through #me_core_module:hook/<feature>_tick, so a module that is not installed simply contributes nothing to the tick.
