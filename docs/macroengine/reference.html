Function reference

How to call the engine, and the ids each module publishes.

The calling convention

Every public id is me_<module>_module:<path>. There is no api/ or systems/ segment in the id — those were the organising folders of the original pack and carry no meaning once the namespace already says which module a function belongs to.

Arguments travel through storage macroengine:input. A function documents the keys it reads in its own header:

# me_cb_module:cb/run
# Executes a raw command string via a temporary command block.
#
# INPUT  (storage macroengine:input cb):
#   cmd   (string)  — the command to run  [REQUIRED]
#   x     (int)     — CB block X          [default: 0]
#   y     (int)     — CB block Y          [default: -64]

So a call is: write the input storage, then call the function.

data modify storage macroengine:input cb.cmd set value "say hello"
function me_cb_module:cb/run

Return values

Functions that answer a question return 1 or 0, so they compose with execute if function:

execute if function me_perm_module:perm/check
    run say allowed

Modules that are off by default

perm has an enforcement switch. With it off, or with the module not installed, permission checks pass rather than fail — a server without the permission module is not a server where nobody may do anything.

Extension points

Two tag families let you attach to the engine without editing it. Both live in the core pack and both merge values from other packs.

Hook slots — #me_core_module:hook/<slot>

Call a slot and every pack that filled it runs. The core defines the slot; modules and your own pack add to it.

Event extension points — #me_core_module:events/<event>

Fired by the event bus; add your function to the tag to receive it.

events/on_death
events/on_enchant
events/on_join
events/on_jump
events/on_lc

Add to a slot from your own pack. Write the same tag id in your pack’s namespace with "replace": false and your values. The game merges the two definitions. Mark a value {"id": "...", "required": false} if the pack providing it might not be installed — that is what keeps a server with a partial install from failing the tag.

Ids by module

The full public id list, per module. Internal implementation paths are not listed: they are not a supported surface, and calling one is a bug that the architecture checks report.

Not every id has a description. 466 of the 756 public functions carry a header comment in the source; the rest ship without one, and this page shows them with a dash rather than inventing a summary. If you need one of those, read the function body — it is short, and the input keys are visible in the first few lines.
