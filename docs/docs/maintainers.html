Maintainer guide

The guard, the gates, the release flow and the archive rules — what is enforced by code and what is only a convention.

Read this before changing anything. Almost every rule below is backed by a check that will fail your build or your commit. That is deliberate: a policy that only lives in a document gets skipped under deadline pressure.

The repository guard

scripts/repo/datapack_guard.py is a fail-closed check that runs in pre-commit, pre-push, CI (job datapack-guard) and Gradle (guardArchives). It refuses:

  • new datapack content under a live path;
  • revived archived tooling;
  • blocklisted accounts (by login and by numeric user id);
  • a tripped kill switch;
  • an archive registry that disagrees with the tree.

The hooks are off by default. Nothing is blocked until git config core.hooksPath scripts/git/hooks has been run, and even then --no-verify bypasses them. The real gate is CI, not the hook.

Archive rules

Archived content is frozen read-only history. Concretely:

RuleEnforced by
Every archived project is registered in archived/archive.jsoncheck_archive.py
original_path must no longer existcheck_archive.py
No workflow may live under archived/check_archive.py
A registered path must start with archived/check_archive.py
A non-datapack successor must resolve to a real pathcheck_archive.py + tests
archived/ is not a Gradle scan rootsettings.gradle

Do not revive archived content. If something archived is needed again, it comes back as a new project with its own review, not by flipping a flag. The one exception this project made deliberately is documented: warnings were added to archived packs to tell players the truth about their status, and that change is recorded rather than presented as routine maintenance.

The two kinds of gate

In-pack load gate

A consent flow: the pack does not operate until a player agrees, and other packs query it through gate/is_open. This is a runtime behaviour inside a datapack. It cannot be enforced by the repository.

Repository gate

The guard and the archive validator. This protects the repository. It has no effect on a world that already has a pack installed, and no effect on a fork. Saying otherwise would be the exact overclaim this project has corrected before: policy distribution is not the same as enforcement.

Release flow

  1. Tests must pass: python3 -m unittest discover -s scripts/tests.
  2. python3 scripts/repo/check_archive.py --strict.
  3. python3 scripts/repo/datapacks_disable.py verify.
  4. Workflow lint (actionlint) and bash -n on shell scripts.
  5. Release publishing stays disabled until an append-only design is reviewed. The job is present but gated with if: false — that is a deliberate policy marker, not a bug to "fix".

Backups

scripts/ops/backup-org.sh is run by a workflow. Two properties are structural rather than conventional:

  • The dependency is pinned and hash-verified, installed into a private virtual environment, and the install runs with the token variables stripped from the environment. An untrusted package install never sees the credential.
  • Encryption defaults to gpg. Asking for an unencrypted archive while the artifact leaves the machine is refused outright, not warned about.

What this project will not claim

  • A green build does not prove a site deployed. Fetch the published artifact.
  • A label does not silence a security check.
  • A warning is not an audit, and a gate is not a sandbox.
  • Partial or paginated data is never presented as complete; a check that could not run reports that it could not run.
